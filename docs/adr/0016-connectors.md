# 0016. Connectors in two layers over MCP

- Status: Accepted
- Date: 2026-10-14

## Decision

**Layer 1, the organization connects once.** `connector_connections` holds an org's connection to an MCP server: connector id (from our catalog), server URL (https), auth type and the credential (OAuth tokens or an API key, as JSON), envelope-encrypted like provider credentials and bound to `(org_id, id)`. One active connection per connector per org; reconnecting replaces it and moves the agents' grants over. Disconnecting deletes the grants. Secrets are never returned by any API.

**Layer 2, each agent gets a subset.** Grants live in `agent_scopes` with the connection id. A grant is accepted only if the connection is active in the org and the scope exists in that connector's catalog (`connectorGrantValidator`). Giving an agent a grant is an admin's call (`manage_agents`), on every path: `PUT …/agents/{id}/scopes`, `PUT …/agents/{id}/access` and a `request_permission` approval. The agent's owner, when not an admin, may only narrow its access (drop grants it has, add tool denials), so whoever an admin made responsible for an agent can't hand it the org's connectors.

**Catalog** (`CONNECTOR_CATALOG`, code we own): for each connector (seeded: GitHub, Sentry, Linear, a Drive-like server) the scopes with labels, and a map from each MCP tool name to one of our scopes, with `sensitive` and an approval-title template. A tool the server lists but the catalog doesn't is never exposed. Merge, deploy and rollback stay sensitive regardless (0015).

**MCP client.** The connector `ToolSource` lists each connected server's tools with the official TypeScript SDK (`@modelcontextprotocol/sdk`, streamable HTTP, bearer token), caches the list for a minute, keeps catalog tools, and exposes them as `<connector>_<tool>` with the server's JSON Schema. Calls open a session through `McpConnect` (tests plug an in-process server via `InMemoryTransport`) and go through the Tool Gateway like every other tool. An unreachable server hides its tools for that turn.

**OAuth.** `startOAuth` (admins, `manage_connectors`) creates a single-use state (only its SHA-256 is stored), a PKCE verifier (sealed) with an S256 challenge, a 10-minute expiry and the person who started it, and returns the provider's authorize URL. The callback (`GET /api/app/connectors/oauth/callback`, session cookie) checks the state is unused, unexpired and the same person (still an admin), exchanges the code with the verifier and stores the tokens sealed, then redirects to the web app. Tokens expiring within a minute are refreshed before a call. Provider OAuth apps come from `CONNECTOR_*_CLIENT_ID/SECRET`; without them a connector can still be connected with an API key.

## Consequences

- Adding a connector is a catalog entry (and optionally OAuth endpoints); no migration.
- Tool output from MCP servers is untrusted content; it reaches the model only as a tool result.

## Addendum (2026-10-14): MCP-native OAuth and custom servers

**Custom MCP servers by URL.** An admin connects any https MCP server. The URL (and every URL learned from it: protected-resource metadata, authorization server endpoints, registration) passes the SSRF guard of ADR 0019. With an API key it is stored sealed; without one we probe the server: an open server connects at once; a `401` leads to OAuth discovery; otherwise the app asks for a key (`needs_key`). Each custom server is its own `connector_connections` row (`connector = custom:{id}`).

**MCP-native OAuth.** Discovery from `WWW-Authenticate: Bearer resource_metadata=…` or `/.well-known/oauth-protected-resource` (with and without the path), authorization server metadata by RFC 8414 (path insertion) then OpenID discovery, Dynamic Client Registration (RFC 7591, public client, `token_endpoint_auth_method: none`) stored per org and issuer in `oauth_clients` (a secret, if issued, is sealed), and the authorization code flow with state, PKCE S256 and the `resource` indicator (RFC 8707) on both the authorize and token requests. Refresh uses the registered client's token endpoint. Catalog connectors with a fixed OAuth app (GitHub, Sentry, Linear, Google Drive) keep using that app; a catalog entry without one would use the native flow. API keys stay as the last resort.

**Tools of custom servers are hidden until classified.** Every listed tool is stored in `custom_tools` with the server's `readOnlyHint`; an admin classifies each as `read`, `write` or `approval` and gives it a label in Portuguese. Only classified tools are offered, with scopes `custom:{connectionId}:read` (read) or `custom:{connectionId}:write` (write and approval); `approval` tools are sensitive, so every call is an approval request titled "{server}: {tool label}". Re-listing (`refresh`) adds new tools unclassified and marks removed ones.

## Addendum (2026-10-16): tools come classified; sensitive tools only ask or stay off

Listing a server's tools classifies each (`connectors/classify.ts`): the server's annotations first (`readOnlyHint` → read, `destructiveHint` → approval and sensitive), then the verb in the name (read verbs, write verbs, and sensitive verbs: delete, remove, send, pay, publish, transfer, refund, unbind, share, merge, deploy, rollback…), and for ambiguous names the shared Judge suggests a level and a reason code, in batches, cached per connection and tool name (`suggestion_source = judge`); judge failures suggest approval with reason `unknown` and are asked again on the next listing. A tool stays "pending" until a person confirms it (`confirmed_at`). Sensitive tools may only be `approval` or `off` (the API refuses read/write; the tool source marks them sensitive whatever is stored, and a re-list turns a stored free level back to approval). `write` tools run without approval and each call is audited (`connector.tool_changed`). The API returns readable name parts and a subject per tool; the web says them in the person's language.

## Addendum (2026-10-27): a custom server's own icon

A server connected by address shows the icon it lists in `serverInfo.icons` (MCP 2025-11-25, from `initialize`), read on every listing of its tools (`connectors/server-icon.ts`). We follow the spec's security rules for icons: only a `data:` URI or an https URL on the server's own origin, through the SSRF guard of ADR 0019, without credentials or redirects, with a 5 s timeout and at most 256 KB; only PNG, JPEG or WebP (no SVG: it can carry script, and the phone app can't draw it), typed by its bytes (a declared type must agree), at most 1024 px a side, and stripped of metadata. The icon is kept in the platform store (S3, `FILES_DIR` or Postgres) under the org's prefix (`orgs/{orgId}/connector-icons/…`, so in Postgres it goes with the org) and a content-hash name and served to the org's members by `GET /api/app/connector-icons/{orgId}/{connectionId}/{file}` (`connector_connections.icon`), so no browser loads anything from the server, and nothing about who uses it reaches the server or a third party. A catalog brand icon wins when there is one. A server that stops listing icons gets the monogram again; when all its icons fail, the last good one stays. We don't guess an icon from the server's website: that would mean fetching pages the server didn't point us to.


## Addendum (2026-10-30): a new connection is every agent's

Agents start with the basics and people take access away where they want. A first connection of a catalog connector (`storeConnection` with no active one to replace) and a new server by address (`storeCustomConnection`, not the same address again) give every active agent the whole connection (`connector:*`, "Ler e escrever") in the same transaction, each grant an `agent.access_changed` audit row by the person who connected (`grantToEveryAgent`). Connecting is an admin's call (`manage_connectors`), and so is giving grants (`manage_agents`): both are admin permissions. The same holds for every client: the web's dialog, the phone and the API. The dialog's last step ("Quem pode usar") starts from these levels, with "Todos os agentes" on top, so an admin confirms or lowers them. Reconnecting keeps the grants as they are. Nothing else changes: sensitive tools ask for approval at any level (0015), a server's tools reach agents only once classified, and mailboxes (0038) and databases (0039) keep their own grants, none given by default.

## Addendum (2026-10-30): reads through Composio's executor

Composio's MCP server runs every app through a few meta tools, marked `destructiveHint`, so each call asked a person, reading pull requests too. The custom source now knows four of them by name. `COMPOSIO_MULTI_EXECUTE_TOOL` says which actions a call runs (`composioActions`: only the documented input, 1 to 50 slugs, no `COMPOSIO_` slug inside, anything else asks as before): when every action only reads, the gateway runs the call as the connection's read (`custom:{id}:read`, when the agent may read the server), so policy, scope, audit and team actions all see a read. A slug reads (`actionLevel`) only when the verb right after its app is get, list, search, find, fetch, check, download, count, describe, view, lookup or read, no other word is a verb, `query` or `replace`, nothing in it is open-ended (`openEnded`: GraphQL, SQL, a mutation, a proxy, a query it runs) and no word sends, deletes or pays in any form. So `GITHUB_LIST_PULL_REQUESTS` reads, while `SHOPIFY_GRAPH_QL_QUERY` (mutations too), `GOOGLEBIGQUERY_QUERY` (any SQL), `GOOGLESHEETS_FIND_REPLACE` and `GITHUB_MARK_NOTIFICATIONS_AS_READ` ask. A wrong guess only makes a call ask. Any other call asks, its card titled by its actions, and may be approved for good per action (ADR 0015). `COMPOSIO_REMOTE_WORKBENCH` and `COMPOSIO_REMOTE_BASH_TOOL` run code that can call any action, and `COMPOSIO_PROXY_EXECUTE` sends any HTTP request to a connected app's API, so they always ask and are never remembered, whatever their annotations or stored level.

## Addendum (2026-10-31): what MCP OAuth asks for, how it authenticates, one refresh at a time

Servers that refused or broke our OAuth showed what the native flow missed. Scopes: when the protected-resource metadata at the server's path lists none, we ask for the root metadata's, if it names the same authorization server (Square refuses an authorization without a scope), and `offline_access` goes with the scopes we ask for when the authorization server lists it (Vercel gives a refresh token only for it), never alone, since no scopes means the server's defaults. The scope is worked out on every authorization (`oauthScope`), not taken from the registered client, so a client still in use that was registered without `offline_access` asks for it on the next one. Client authentication: the registration asks for `none` (a public client with PKCE) when `token_endpoint_auth_methods_supported` lists it or is absent, else `client_secret_post`, else `client_secret_basic`, and the method the registration answer names wins; an answer that gives a secret for `none` without naming a method is kept as `client_secret_post`. The method is kept on the client (`oauth_clients.token_auth_method`, null for clients registered before, which keep sending any secret in the form), and the secret stays sealed and goes the way the method says, at the code exchange and on every refresh, by HTTP Basic with each part form-encoded first (RFC 6749 §2.3.1). A refused registration keeps the server's own `error` and `error_description` (one line, at most 200 characters, nothing else from the answer), returned as `detail` with `not_approved` and shown under our message. A connection's tokens are refreshed once at a time, so two calls never spend the same refresh token (servers that rotate it would refuse the second, and the connection would break), and no transaction stays open while the provider answers: native mode's PGlite runs every query through one transaction lock, so the whole server would wait, and on Postgres each waiting call would hold a pool connection. The call that takes the connection's lease (`connector_connections.refreshing_until`, 30 s, a conditional UPDATE on the tokens it read) asks the provider; the others read the row until the tokens change, or until the lease ends and one of them takes it over. Within a process, calls that need the same refresh share it. The new tokens are written only over the ones refreshed, so a reconnect meanwhile keeps its own, and the token request gives up after 15 s, well inside the lease. The refresh of an MCP OAuth connection sends the resource it was authorized for (`connector_connections.resource`), since the MCP authorization spec wants it on every token request. One-click presets can say how their server takes an API key (`keyScheme`: Semrush's is `Apikey`, the others `Bearer`) and that the Cloud offers no key for it (`cloudOAuthOnly`, Intercom's US and EU servers). Intercom's server does take an access token, but its terms forbid an app asking its users for theirs, and on the Cloud agentes.chat is that app. Self-hosted, a workspace connects its own data, which is what those tokens are for, so the key stays.

## Addendum (2026-10-31): several accounts per MCP server

Amended by ADR 0099. A server's address connected again is another account of it, not a new sign-in: "Reconectar" names its connection (`connectionId`). Every account is every agent's. Tool names start with each connection's stored `tool_prefix`, set once, not with its label, so renaming never renames tools. Catalog connectors keep one connection each.

Amended by ADR 0107. The catalog is GitHub, Sentry and Linear: the Drive-like entry, its address field (`needsServerUrl`), its Google OAuth app (`CONNECTOR_GOOGLE_*`) and the `serverUrl` override of `startOAuth` and `POST …/connectors` are gone, and migration 0156 disconnects any native Drive row. ## Addendum (2026-11-03): GitHub's current tools, Projects and Actions, and what a sign-in lacks

GitHub's remote MCP server renamed its tools (`issue_read`, `issue_write`, `pull_request_read`, `actions_list`, `projects_write`…), and a tool our catalog doesn't name is never exposed, so agents couldn't create an issue or read a pull request through the connector and fell back to signing the person in to gh on their computer, which leaves the person's own token there, outside the scopes, approvals and git proxy.

- **The catalog follows the server's current names** (its README, read 2026-11-03), with new scopes `actions.read`, `projects.read` and `projects.write` (on with the connection, like the rest). `pull_request_review_write` (it can approve) and `actions_run_trigger` (it can deploy) are sensitive.
- **Toolsets and scopes.** The remote server loads only context, repos, issues, pull_requests and users unless asked, so the catalog entry carries `headers` (`X-MCP-Toolsets: …,actions,projects`), sent with the sign-in. The OAuth sign-in asks for `project` too (Projects v2 needs it).
- **What a sign-in lacks.** `connector_connections.oauth_scopes` keeps what a catalog sign-in granted (the token's `scope`, else what we asked for; sign-ins from before were backfilled with the catalog's scopes of that time). A connection whose sign-in lacks some of what the catalog asks for now shows a line saying what Reconectar adds ("Reconecte o GitHub para os agentes também poderem usar o GitHub Projects"), on the web and the phone, and keeps working as it is until then.
- **Agents are told** (`GITHUB_GUIDANCE`, with GitHub only): the connector and git through our proxy, read-only gh runs without asking where gh is already signed in, never sign the person in to gh nor ask for a GitHub token, and when the connector lacks something say what and that an admin can reconnect.
- Reconectar moves the connection's "Aprovar sempre" rules to the new connection with the agents' grants, so asking everyone to reconnect for Projects never makes them approve again.

## Addendum (2026-11-12): a server's `destructiveHint` suggests, our verbs lock

A server marks a harmless tool (moving a task) `destructiveHint` as easily as a dangerous one, and a locked tool asked on every call for good. The annotation now only suggests: the tool starts at `approval` with reason `destructive_hint` and `sensitive = false`, so an admin can give it any level, and "Aprovar sempre" and the agent's approvals level apply as for any tool that asks. The lock comes only from our own rules: a sensitive verb in the name (`verb_sensitive`; with the hint, one of those words in any position of the name), Composio's meta tools, and a Composio toolkit's actions, whose hint is our rule for them (ADR 0107 §5) and is enforced on every call. A hint that arrives after an admin chose `read` or `write` moves the tool back to `approval` once, still unlocked. The `destructive_hint_suggests` migration unlocks the rows stored for the hint alone and keeps their level, by the same word rule as the classifier.

## Addendum (2026-11-15): servers on the older HTTP+SSE transport, and pasting a server's configuration

Some MCP servers still speak only the older HTTP+SSE transport (protocol 2024-11-05): their address is an event stream that takes GET alone, names where messages go (`endpoint`) and answers on the stream. A POST there got 404 or 405, so the server was refused (`connector.mcp_status`). And the setup a vendor documents is often a `claude mcp add …` line or an `mcpServers` block, not an address.

- **One session, Streamable HTTP first.** `openHttpSession` (`connectors/mcp-sse.ts`), behind `connectOverHttp`, opens Streamable HTTP and falls back to the SDK's `SSEClientTransport` only when the POST is refused with 404 or 405, as the MCP spec's backwards-compatibility section has clients do. Every other refusal (401, 403, 400, 5xx) is the server's answer and never retried over SSE. The same headers go on the stream's GET and on every POST, through the same guarded fetch. The SDK waits for `endpoint` without a limit, so the session is given up after `SSE_OPEN_MS` (30 s) and its transport closed.
- **Nothing is stored.** No column says which transport a connection uses: each session tries Streamable HTTP first (one quick 404 or 405 more per session for such a server), so a server that moves to Streamable HTTP is used that way at once.
- **The probe.** `probeMcpServer` answers a POST's 404 or 405 with a GET asking for `text/event-stream`: a stream is `open` (its body cancelled), a 401 or 403 there goes through the usual OAuth discovery, anything else keeps the POST's refusal.
- **A refused key** marks the connection to reconnect over either transport (`refusedCredentials`: a `StreamableHTTPError` or an `SseError` with code 401).
- **Pasting.** `parseMcpPaste` (`packages/client/src/lib/mcp-paste.ts`, pure, never throws) reads `claude mcp add` (with `--transport`, `--header`, `--env`, continued lines), `claude mcp add-json`, an `mcpServers` block (Claude, Cursor; VS Code's `servers`, Windsurf's `serverUrl`, a single entry, `mcp-remote` as the address it reaches), `npx`/`uvx`/`docker run` lines and a bare address. It returns the address, the name and each header as a name and value with the terminal variables or placeholders in it (`$X`, `${X}`, `${env:X}`, `<your key>`, `YOUR_API_KEY`), filled from the paste's own `env` or `-e`. A server run as a command (stdio) is recognized and refused in words: this server never runs a workspace's processes. The web form reads the pasted text (never the field's value, which loses its line breaks): the address and name go in their fields, a literal `Authorization: Bearer` becomes the key, a key written as a variable is asked for, and every other header goes to the form's request headers (ADR 0186), its value empty when it was written as a variable. Nothing new crosses the API: the form sends `serverUrl`, `label`, `apiKey` and `headers`, as it does when they are typed.
- **Later.** Request headers of their own for a server by address, filled from a paste; a choice among several servers in one block (the first by address is taken); the phone's connect sheet.

## Addendum (2026-11-15): servers that take no key, and tools that call or buy under other words

Five more one-click servers, each checked on 2026-11-15 like the others (401 with OAuth, a `registration_endpoint`, PKCE S256): AgentMail, AgentPhone, Vapi, Whop and You.com. Two things the catalog couldn't say before:

- **`oauthOnly`**: the server takes no API key in `Authorization`, so neither the Cloud nor a self-hosted server offers one. Vapi's refuses keys ("The hosted server no longer accepts Vapi API keys"), AgentMail's wants its key in `x-api-key`, and Whop's documents only its OAuth. `cloudOAuthOnly` stays for a server that takes a key the vendor's terms forbid asking for (Intercom). One predicate, `takesKey`, decides both for the listing's `auth` and for a key sent anyway (`connector.oauth_only`), so the apps hide the key field by `auth` as before.
- **`askTools`**: a preset's tools that place calls, buy or write to people under words our verbs don't catch (AgentPhone's `make_call` and `buy_number`, Vapi's `create_call`, AgentMail's `reply_to_message`): they start at `approval` with the judge's own reason (`reaches_people`, `spends_money`) and stay locked there (`sensitive`), like a tool whose verb sends or pays, whatever the server's annotations say. A name the server renames falls back to our usual rules.

Left out on purpose: Telnyx (`api.telnyx.com/v2/mcp`) and Agentcard (`mcp.agentcard.sh/mcp`) have official servers with OAuth, but both answer `initialize` and `tools/list` without credentials and ask only at `tools/call`, so our probe reads them as open and would store a connection signed in as nobody. Telnyx also reaches its whole API through one `invoke_api_endpoint` tool, and Agentcard's `get_card_details` reads as a free read by its verb. Each needs its own decision before joining the catalog (taken in the addendum of 2026-11-17).

## Addendum (2026-11-15): an OAuth app the admin registered, for servers that register none

Some MCP servers have OAuth but take no Dynamic Client Registration: corporate identity providers (Microsoft Entra ID, for one) register apps only through their admins. Those answered `needs_key` with `not_approved` and could be reached only by an API key, if any. The admin can now bring an app registered there: `POST …/connectors/custom` takes `oauthClient` (`clientId`, an optional `clientSecret` for a confidential app, optional `scopes`), and the authorization goes on as before, with state, PKCE S256 and the `resource` indicator, the token exchange and every refresh by that app. The admin registers `…/api/app/connectors/oauth/callback` (from `PUBLIC_URL`) as its redirect URI, which the web form shows.

The app is a row of `oauth_clients` with `preregistered = true` (migration 0293). Dynamic registrations stay one per org and issuer (`oauth_clients_org_issuer`, now partial on `not preregistered`), and `ensureOAuthClient` never reads, reuses or overwrites an admin's app. Admin apps are one per org, issuer and client id (`oauth_clients_org_issuer_app`): two servers on one tenant may use two apps, and a second app never changes the client under the first one's connections. The same client id again updates its row in place (a rotated secret, other scopes), and a blank secret keeps the saved one, so typing the id again to change the scopes doesn't make a confidential app public. The secret is sealed like a registered client's (`oauth-client|{org}|{id}`), never returned, and goes by HTTP Basic, the method every authorization server must take (RFC 6749 §2.3.1), unless the server lists only `client_secret_post`. Without a secret it is a public client, PKCE alone. The admin's scopes replace the ones the server lists, and `offline_access` joins them when the authorization server lists it, as for any scope we ask for (`oauthScope`).

Later sign-ins without the app ("Reconectar", another account of the same address) use the app the reconnected connection used, else the newest one an active connection to that address uses (`adminOAuthAppFor`). With every connection to it revoked the server answers `not_approved` again and the admin types the app again: whether the old app still stands is theirs to say. A server without protected-resource metadata whose own origin has an authorization server without a registration endpoint still needs a key, except with an admin's app (`probeMcpServer`'s `ownApp`). An `apiKey` in the same request wins, as before.

Later: the phone's connect sheet offers the same form (today only the web does, and only after a `not_approved`). The web offers no way to type the app again while a connection to that address stays, since a sign-in then goes straight through the saved app: rotating an expired secret or changing the scopes is an API call (`oauthClient` with the same client id) until an admin's app can be listed, edited or removed on its own. Neither does it offer the app to a server without protected-resource metadata, which answers a plain `needs_key`.

## Addendum (2026-11-17): services that answer anyone, and services whose every call a person decides

Telnyx and Agentcard join the catalog. Both answer `initialize` and `tools/list` to anyone and ask for credentials only when a tool runs, so the probe read them as open servers and would have stored a connection signed in as nobody. A preset now says so itself, with `signInRequired`, and no answer of such a server is ever "open": `probeMcpServer` takes the option and, after a 200 (or an event stream on the older transport), reads the protected-resource metadata and, failing that, an authorization server at the server's origin, else answers `needs_key`. Headers a person typed are no sign-in either. `signInRequired: "key"` is for a service that documents an API key alone: connecting without one answers `needs_key` and sends nothing to the server, and the catalog lists the key alone.

- Telnyx (`https://api.telnyx.com/v2/mcp`): "Bearer authentication with `Authorization: Bearer <TELNYX_API_KEY>`" (developers.telnyx.com/docs/development/mcp/remote-mcp), and "No OAuth/PKCE in v1" in its server card (telnyx.com/.well-known/mcp/server-card.json), both read on 2026-11-17. Its server published protected-resource metadata on 2026-11-15, but we follow what its documentation promises: the key alone.
- Agentcard (`https://mcp.agentcard.sh/mcp`): "A browser sign-in appears the first time a tool runs", or `Authorization: Bearer` with an organization's client secret (docs.agentcard.com/tools/mcp, read on 2026-11-17). Its metadata names its authorization server, so it signs in, or takes a key.

One reaches a whole telephony API through one tool (`invoke_api_endpoint`: calls, messages, numbers bought), the other moves money (cards, funds, purchases). Their presets set `everyCall`: every tool asks, the ones a server lists later too, locked like a send (`sensitive`, so an admin can only leave it asking or turn it off), with the reason `askTools` gives it (`spends_money`, `reaches_people`) or the new `every_call`. The tool source reads it from the preset at each call (`ToolDefinition.everyCall`), not from the stored levels, so a connection made by address before the preset asks too. A person decides each call on its own: the Tool Gateway offers no "Aprovar sempre" for it (`rememberKinds`), and it is never approved ahead nor made a routine's own action (`aheadRefusal`, which `ownJobCovers` and "Sempre nesta rotina" read first). Every tool loses "Aprovar sempre", not only those that spend, call, send or buy: with one tool running any endpoint, a name doesn't say what a call does.

The card says what the call will do and how much it moves: a preset names the arguments for both (`callArgs`: Agentcard's `request` and its amounts in US cents, `amount_cents` and the like; Telnyx's `endpoint_name`), the approval's view carries which ones the call holds (`ApprovalView.callArgs`), and the apps lead the card's values with them, the amount in dollars, the ask cut on the card's face, never left out.

An agent set to "Nunca perguntar" still asks for nothing (ADR 0173, as amended 2026-11-12), so a service whose every call a person decides is not its to use: none of the tools of an `everyCall` preset is offered to it, and a call it makes anyway is refused by the run policy (`REFUSALS.everyCallNever`, `refusal: "policy"`), which tells the model to say that only an admin, by setting the agent's approvals to a level that asks, can change it. Nothing is spent or sent without a person's yes, and the agent's level keeps meaning what ADR 0173 says. The agent's access says why, where the level is set: the access tree carries `everyCall` per connector (`GET …/agents/{agentId}/access`), the agent's access tab and the workspace's access matrix on the web mark the row unavailable at that level instead of "asks for approval" (`offAtNever` in `packages/client/src/lib/access-levels.ts`), and the phone's access screen and the agent's profile say the same. A routine, or a run nobody is behind (a run an agent's message started), already asked for each call at every other level, with no "Aprovar sempre" and nothing approved ahead: the approval goes to the people who may decide it, and a test now holds both.

Two of Agentcard's tools are withheld (`withheldTools`): never listed, stored or offered, whatever an admin sets, and a connection made before loses them at its next sync while the tool source drops them in any case. `get_card_details` answers with the card's number, expiry and CVV, which would stay in plain text in the agent's history, its run's steps and the audit log. Nothing we have keeps a result the model reads out of those: the Vault's sealed path carries only an item's password to the runner and never shows it to the model (ADR 0144), `request_secret` asks a person for a value instead of taking one from a tool, and the masking of a tool's details and of the audit (`redactCredentials`, `auditInput`) recognizes credentials' formats, not a card's. Agentcard's documentation (docs.agentcard.com/llms-full.txt and /tools/mcp, read on 2026-11-17) says "The card object never carries the number or CVC", and only reading a card's credentials returns "the number, expiry and CVC": a purchase goes through `buy`, whose result names the card by brand and last four digits. `approve_request` would let the agent approve its own spending request, a decision that stays with a person in Agentcard's own app, and the same page says it answers `personal_surface_only` on a connected session anyway. Offering either needs a new design: a result sealed for the browser or the runner the way the Vault's logins are.

These locks go by the host, not by the address a preset lists. A connection whose server is on Telnyx's or Agentcard's host is that service's however its address was typed, pasted or stored: with a query, in another case, with extra slashes, at another path. `presetLocks` gathers the locks of every preset on the address's host (its hostname in lower case, without a trailing dot): `signInRequired` when it connects, `everyCall` and the withheld tools at each listing and call, `askTools` at each sync, `callArgs` on the card. A connection stored before under such an address gets them at its next listing, with no migration, since every one of them is read at use. What names a connection and draws its mark stays `presetForServer`, on the preset's own address.
