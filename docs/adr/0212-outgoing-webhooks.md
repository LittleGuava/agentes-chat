# 0212. Outgoing webhooks: a workspace's events, signed, to an address its admins chose

- Status: Accepted
- Date: 2026-11-15
- Builds on: ADR 0005 (the Postgres outbox: deliveries are jobs, retried with its backoff), ADR 0007 (sealed secrets), ADR 0085 (permissions: `administrator`), ADR 0106 (routines started by a webhook: the incoming side and its `X-Agentes-Signature`), ADR 0151 (who sees what: administrators read every channel, never a DM)
- Code: `packages/engine/src/outgoing-webhooks.ts`, `packages/db/src/schema/outgoing-webhooks.ts` (`outgoing_webhooks`, `outgoing_webhook_deliveries`), migration `0295_outgoing_webhooks`, the hooks in `messages.ts` (`insertMessageWithRuns`), `runs.ts` (`transitionRun`) and `issues.ts` (`createIssue`), job `webhooks.deliver` in `jobs.ts`, routes `apps/server/src/routes/app/outgoing-webhooks.ts`; the notice `webhook_disabled` (`notifyWebhookDisabled`, `resolveWebhookDisabled` in `notification-producers.ts`); the screen `apps/web/src/components/webhooks/OutgoingWebhooksSection.tsx`, its client `packages/client/src/webhooks/*` and words `packages/client/src/lib/outgoing-webhooks.ts`

## Context

agentes.chat takes events in (GitHub, Sentry, a routine's own address, ADR 0106) but tells nothing to the systems a team already runs: a CRM that wants to know a task was created, a log that keeps what agents did, an automation that reacts to a message in `#vendas`. Teams ask for the other direction: "call this address when X happens". Whatever we send leaves the workspace, so it must be chosen by someone who may read it, never carry a DM, never reach this server's own network, and never slow the chat down.

## Decision

1. **A webhook is an address, a secret and a set of events**, made by a member with `administrator` (ADR 0085): what it sends includes private channels' messages, which only administrators read (ADR 0151). `outgoing_webhooks` keeps per workspace (at most 20): a name, the URL, the events, the channels it listens to (`channel_ids`), the secret sealed (envelope encryption, ADR 0007, bound to the workspace and the webhook), who made it, and its health (`consecutive_failures`, `last_success_at`, `last_failure_at`, `disabled_at`, `disabled_reason`). Every change is audited in the incoming webhooks' area, so the audit log already has words for it (`webhook.outgoing_created|outgoing_updated|outgoing_deleted|outgoing_secret_changed`).
2. **Three events, then more.** `message.posted` (a message in one of the channels chosen; at least one channel is required for it), `run.finished` (an agent's run ended: done, failed or canceled), `issue.created` (a task was created). The channels chosen narrow every event that has one; with none, `run.finished` and `issue.created` come from every channel. `ping` is only the test (§8).
3. **Never a DM.** Only channels of kind `channel` are ever chosen or sent from: a DM, a routine's room (a DM with the agent) and a task's conversation are not, checked when the webhook is saved and again in the statement that queues each delivery. A task with a restricted audience (made in a DM, or limited to some people) is not sent either. A run carries ids and its status, never its reply's text.
4. **Queued in the change's own statement, built when sent.** The delivery rows and their `webhooks.deliver` jobs are written by one `insert … select` from the webhooks that match, in the same transaction as the message, the run's end or the task (a message's in its own insert statement, `insertMessageWithRuns`): with no webhook in the workspace it is one indexed lookup that writes nothing. A delivery keeps only the event and the id of what it is about (`subject_id`); its body is built from the current rows when it is sent, so the log is never a second copy of the chat, and a message or a task deleted before then is `skipped`. Messages written outside `insertMessageWithRuns` (a mission's own log, a task conversation's copies, a thread moved) are not events.
5. **The request.** `POST` to the URL with `Content-Type: application/json` and a body `{ id, type, createdAt, sentAt, orgId, data }` (`id` the delivery's, the same on every attempt, for the receiver to drop repeats; `sentAt` this attempt's time, for it to refuse old ones). Headers `User-Agent: agentes.chat-webhooks`, `X-Agentes-Webhook-Id`, `X-Agentes-Webhook-Event` and `X-Agentes-Webhook-Signature: sha256=<hex>`, the HMAC-SHA256 of the raw body under the webhook's secret. A header of its own, not ADR 0106's `X-Agentes-Signature`: a routine's address checks that one over the same raw body, so a webhook pointed at a routine would otherwise pass as a signed call under the routine's secret only by accident of naming.
6. **SSRF, at save and at every send.** The URL must be `https`, without a user or password, and every address its host resolves to public (`assertPublicHttpsUrl`, as a custom MCP server's), when it is saved. Each attempt goes through `outboundFetch` (checked and pinned at connect time, so a name that changes later can't move it; the server's own network only where its operator allows it, `allowPrivateOutbound`), made at send time, with `redirect: "manual"`: a redirect is a failure, never followed. A refused address fails the delivery at once, no retry.
7. **Retries, then off.** Each attempt waits 10 seconds at most and reads no answer body. A 2xx is `delivered`. A timeout, a network failure, a 408, a 429 or a 5xx is retried by the outbox with its backoff (ADR 0005), six attempts in all over about 45 minutes, each retried one logged as a warning (the receiver's trouble, not the server's error to report); any other answer fails at once. A delivery that fails for good adds one to the webhook's `consecutive_failures` in one atomic update; ten in a row turn it off (`disabled_at`, `disabled_reason = "failures"`); a delivered one sets it back to zero. An admin turns it back on. A workspace suspended or being deleted sends nothing: its deliveries are `skipped` (`workspace_closed`), as a closed workspace's routine address answers nothing (ADR 0106 §4); one on a hold (its agents stopped) still sends. Every outcome is written with a `where status = 'pending'`, so a job that runs twice (a lost lease) neither sends twice after its first ending nor counts a failure twice.
8. **The log and Testar.** `outgoing_webhook_deliveries` keeps per delivery: event, subject, status (`pending`, `delivered`, `failed`, `skipped`), attempts, the last HTTP status and a short error code, never a body. Each webhook keeps its newest 100. `POST …/outgoing-webhooks/{id}/test` queues a `ping` delivery through the same path.
9. **API.** `GET|POST /api/app/organizations/{orgId}/outgoing-webhooks`, `PATCH|DELETE …/{id}` (name, URL, events, channels, `enabled`), `POST …/{id}/secret` (a new secret, shown once, like the first), `POST …/{id}/test`, `GET …/{id}/deliveries`. The secret is shown only when made.
10. **The screen.** Configurações › Conectores › Webhooks, a tab beside the connectors and only for `administrator` (a member never gets it, and the server is never asked). One card per webhook: its name, its address, its state in words (on, off, off after failures), its events and channels, its last delivery; the actions Testar (only while it is on), Edit, New secret, Turn off or on, Delete, and its latest deliveries, each with its result in words. The form checks a name, an https address, at least one event and channels for `message.posted` before sending; the server's refusals (an internal address among them) are said under their field. A secret, the first or a new one, is shown once on its card with Copy and is never in the list's answer. A new secret and Delete ask first, in place. The desktop app shows the same page (ADR 0036). The phone has no screen for it yet.
11. **Telling the administrators.** When ten failures in a row turn a webhook off, every administrator gets a `webhook_disabled` notification in the inbox (the webhook's name and the last error), no push and no email: it waits for someone to look, it asks nothing of them right now. One per time it is turned off (its group carries the moment), closed when it is turned back on or deleted. It opens this screen.

## Consequences

- Each message, run end and task created pays one indexed lookup on `outgoing_webhooks` by workspace; nothing is written when no webhook matches.
- A delivery is quick work for the outbox (10 s at most per attempt), so a slow receiver never holds an agent's run, but it holds a quick slot, which messages' routing and notifications share, for up to 10 s per attempt: a busy channel watched by a slow receiver adds that many quick jobs. A lane of their own is for later if it shows.
- A loop is possible: a webhook pointed at a routine's own address (ADR 0106), whose run writes a message in a watched channel. One run at a time per routine, the routine's 60 calls a minute and the agent's budget bound it, as for any routine.
- A job whose worker died during its last attempt, or whose handler threw on its last one (a secret that no longer opens), is failed by the outbox: that delivery stays `pending` in the log, and is pruned once a day old.
- The body of a retried delivery is built again at each attempt: an edit in between is what the next attempt sends.

## Later

- The screen on the phone.
- More events (a message edited or deleted, a task updated or closed, an approval asked, a routine's report), and a filter by agent.
- An email to the admins when a webhook is turned off (the notification is §11), and replaying a failed delivery by hand.
- A signature that also covers a timestamp header, for receivers that don't read the body's `sentAt`.

## Alternatives considered

- **One `webhooks.event` job per message that fans out later.** An outbox row for every message in every workspace, almost always for nothing; the `insert … select` writes nothing when nobody listens.
- **Keeping the body built at queue time.** Retries would send exactly the same bytes, but the log would hold a copy of every message sent out, surviving its deletion and the channel's.
- **Our own retry schedule.** The outbox already retries with backoff and leases; the handler only needs to know the last attempt (`finalAttempt`).
- **`manage_connectors` as the permission.** It manages what comes in and what agents reach; this sends the workspace's own conversations out, private channels included, which only administrators read.
