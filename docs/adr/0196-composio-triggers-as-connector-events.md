## Context

ADR 0130 made a connector's natural event a routine trigger, and named Composio's triggers as the way in for the services connected through Composio (ADR 0107: Slack, Teams, HubSpot, Google Drive and the rest), "through the same `source`, created with Composio's trigger API instead of an MCP tool". Composio already wakes routines for Gmail and Outlook (ADR 0038), through one webhook for the whole server (`POST /api/webhooks/composio`), signed with the project's secret.

One thing ADR 0130 doesn't cover: a Composio event never reaches the routine's own address. Composio posts every trigger of the project to the one webhook, and the routine is found from the trigger's id. This ADR decides that path, and the first event on it.

## Decision

1. **A connector event has a way.** `CONNECTOR_EVENTS` keeps one entry per event; each says how it is made: `mcp` (ADR 0130: the connection's own tools register the routine's address at the service) or `composio` (a Composio trigger, by its type, on the connection's connected account, for the workspace's Composio user `org_<orgId>`). Both keep what they made in `routine_hooks.source` (`externalId`, `status`, `lastError`), so the routine view, the apps' "Com erro" and saving to retry are the same. No migration.
2. **Made, kept and taken back like a webhook.** The trigger is made when the routine is saved active, and taken back when it is paused, moved to another trigger or connection, deleted, or its agent deleted. A paused routine has none, since Composio bills every delivery (ADR 0038: about $0.003 an event). Each event says which part of its filter Composio can apply (`config`): changing only the rest keeps the trigger, changing that part makes a new one. Composio's create is an upsert, so routines on the same account, trigger type and config share one trigger; it is deleted only when no routine's source holds it any more. Composio refusing it (the trigger isn't enabled for the project, the account lost access) leaves `status: "error"` with Composio's words; without `COMPOSIO_API_KEY` the routine says so the same way.
3. **The first event: a new message in a Slack channel** (`slack.message.received`, Composio's `SLACK_CHANNEL_MESSAGE_RECEIVED`; its older `SLACK_RECEIVE_MESSAGE` is marked deprecated). Its filter: a channel (its id, `C…`, `G…` or `D…`) and words in the text. The channel goes to Composio as `channel_id`, with `is_bot_message: false` always, so a bot's message or one in another channel is never delivered or billed; the words run here, so a message without them still is, and a routine with no channel hears every channel the account sees. Slack's other events (a direct message, a reaction) and the other services in ADR 0130's table are one entry each.
4. **Received only through the signed endpoint.** `handleComposioWebhook` checks the signature (Standard Webhooks, the project's secret), then a `trigger.event` goes to `receiveComposioTrigger`. Each routine whose `source.externalId` is the trigger's id hears it, while it is on, not deleted and its workspace open, and only when the event's connected account is the connection's own (an event naming another account is ignored, as a mailbox's is). The delivery is counted once for the workspace (`composio_usage_days`, `events`, under the trigger type, ADR 0103). Then, per routine, the webhook path's checks: its limit (60 a minute), the event's type and filter, the agent still reading the connection (ADR 0130 §4), and a repeat of Composio's `webhook-id` within 24 hours answered with the first call's run. A call to the routine's own address never runs a Composio event: whoever learned the address can't stand in for Slack.
5. **The agent doesn't act on its own message.** Composio is asked for people's messages only, and here a message with `bot_id`, a `bot_message`, an edit or a delete never passes. A connection that posts as the person (a user token) leaves no `bot_id` on the agent's reply, so before the trigger is made the server asks Slack who the connected account is (`SLACK_TEST_AUTH`, Slack's `auth.test`, at the toolkit's pinned version) and keeps its `user_id` in the source (`selfId`); a message by that user never passes. When the answer names no user, no trigger is made and the routine shows the error ("Slack didn't say which user the connection is"): a routine that could hear its own replies doesn't start. Changing only the words keeps the trigger and the `selfId`; making a trigger again reads it again.
6. **Outside content.** The event's data joins the next run as a webhook call whose body is that data (`x-composio-event` names the trigger type), read by the model only inside `untrustedBlock` (ADR 0117), one run at a time with events arriving together merged (ADR 0106).
7. **Composio turning a trigger off** (`composio.trigger.disabled`) marks the routine's source `error` (`trigger_disabled`) beside the mailboxes' watches; saving the routine makes a new trigger.
8. **The apps.** The routine list names the event ("Quando chegar uma mensagem no Slack"). In the editor on the web and the phone, Quando offers one choice per connector event a connection of the workspace brings (`connectorEventChoices`: "Email no MillionSend", "Mensagem no Slack"), and the routine's own even when its connection is gone; picking another event starts its connection and filter over (`connectorDraftFor`), so a Slack channel never goes out as an email's filter. A Slack routine picks its connection ("Conexão", when there is more than one the agent reads), then the channel's id and the words. The API takes `slack.message.received` in `trigger.event` and `channel`/`text` in its filter, and a Slack connection lists it in `events`.

## Not chosen for the first event

- **Gmail's new email** is already a routine trigger (ADR 0038's email trigger, Composio's `GMAIL_NEW_GMAIL_MESSAGE`): a mailbox is a mail account here, not a connection through Composio. A second way to the same mail would split its rules and its dedupe.
- **GitHub's new issue**: GitHub is the workspace's GitHub App here (ADR 0033, 0156), not a Composio connection; its issues come through the App's webhook as the PR event does (ADR 0130's table), with no Composio bill.

## Consequences

- A Slack routine receives every message the connected account sees and drops what its filter leaves out; each delivery is billed by Composio and counted for the workspace. Past 60 a minute the routine's limit drops the rest (Composio doesn't retry a 202).
- Finding the routine reads `routine_hooks.source->>'externalId'` without an index: a scan of the routines' addresses per delivery, small next to the run it may start.
- The routine's own address still exists (a connector routine is a webhook routine) but runs nothing for a Composio event.
- With a connection that posts as the person, that person's own messages don't start the routine either: Slack shows them and the agent's replies as the same user, so the routine can't tell them apart. Someone else in the channel starts it.
- Making a trigger costs one tool call more (`SLACK_TEST_AUTH`), billed by Composio, counted in the workspace's usage (ADR 0103) and held to its monthly cap (`COMPOSIO_CALLS_PER_MONTH`, ADR 0107 §7) like any other: a workspace at its cap gets the routine's error instead of a trigger. Its answer is read at the top or under `response_data`, where Composio sometimes nests a provider's answer.
- A save by a caller that can't reach Composio (no `connectors`) keeps the trigger the provider holds and its `selfId` together; only making a trigger reads who the account is.
- Reconnecting the connection gives it another Composio account: its routines keep a trigger and a `selfId` from the old one, still shown as active, and saving them doesn't make a new one, because nothing in their source changed.

## Later

- More events, one entry each, with words in the apps and a test: Slack's mention and thread reply, Microsoft Teams' channel message, HubSpot's new contact or deal stage, Google Drive's new file, Google Calendar's event starting, Asana's new task, Intercom's and Zendesk's new conversation or ticket.
- The channel picked from a list (the connection's `SLACK_FIND_CHANNELS`) instead of typed as an id.
- `bun run composio:check` reading each trigger type's schema at Composio before an event ships, as it does for tools, and the tool that says who an account is (`SLACK_TEST_AUTH`) at the pinned version.
- An expression index on `routine_hooks.source->>'externalId'` if deliveries grow.
- On a reconnect (ADR 0107 §4), making the connection's routines' triggers again on the new account, with its `selfId`.
- A filter on thread replies (`is_thread_reply`) and on the channel's kind (`channel_type`), which Composio's trigger takes.
- An agent's own routine tools making connector routines (ADR 0130's consequence still holds).
